# 模块边界与演进路线

## 当前实现

```text
scripts/                    兼容原有 Windows 运行命令
src/unitree_vision/
  config.py                 类型化配置、TOML、CLI 覆盖及提前校验
  camera.py                 相机枚举、推流管理、诊断预览与 SDK 会话
  protocol.py               12 字节帧头 + H.264 access unit，PTS 元数据关联
  streams.py                有界相机帧队列、重连与解码器重建
  state.py                  G1 关节顺序/单位及本地/服务端读取
  pairing.py                同帧号、有界、按提交顺序的配对
  dataset.py                样本提交、校验、离线索引恢复
  collector.py              生命周期、采集调度、CLI 与控制程序接入
```

`config`、`pairing`、`dataset` 与未来模型解耦。`protocol`、`camera`、`state.from_env` 是 OrcaGym 26.8.2 适配边界；升级 SDK 时优先测试它们。固定姿态 CLI 与嵌入式采集共用核心模块。

## OpenPI 方向

以当前画面、机器人状态和任务指令生成短动作段；执行一部分后重新观测。Windows 负责仿真与执行，Ubuntu GPU 机器可以负责策略推理。模型训练与运行环境独立。

1. **观测接口（本次实现）**：头部/右腕图像、实测关节位置/速度、指令、帧号。`collector.poll()` 返回完整配对项，供下一阶段 adapter 使用。
2. **任务理解（待实现）**：单任务传入 prompt；复杂任务再评估增加视觉语言模型。显式按钮编号识别可以独立评估，但不强制用 YOLO 作为 OpenPI 的前置步骤。
3. **动作策略（待实现）**：必须用 G1 数据微调并验证输入/输出契约，不能认为已有 π 模型直接支持本机器人。
4. **执行接口（待实现）**：明确动作维数、单位、绝对/增量、关节/末端坐标系及执行时序。站立和平衡交给现有控制器，初期学习手臂操作。
5. **结果判断（待实现）**：用可部署的视觉/传感器判断成功、重试或停止。仿真真值用于标注和评估，不能混入策略输入。

## 后续 adapter 必须声明的契约

- 模型使用的 profile、`state_names` 顺序与单位，不可任意切片或补零。原始角度不自动转换为夹爪开口。
- 原始帧为 HWC uint8 **BGR**；模型 adapter 明确转换为 RGB，再按其训练配置 resize/crop。保存的 PNG 由 OpenCV 正确编码颜色。
- 明确 OpenPI checkpoint 所需的相机键、图像尺寸、归一化统计和动作 schema；不在本阶段猜测这些键或维数。
- 动作和对应观测的时间关系需确定；原始 `action: null` 不能复制成 `state` 伪造专家动作。
- 策略服务超时、旧观测和异常动作的处理必须由执行模块落实，再接入机器人。

## 迭代验收

先验证统一观测和编号识别，再采集有动作、有结果标签的差异化示范。数据集按完整场景/episode 划分训练与验证，不随机拆相邻帧。测试目标位置变化、指令切换、干扰按钮、轻微目标移动、已完成状态，并比较实时画面与冻结画面的表现。

目标是场景变化后无需改坐标脚本，仍能依据观测完成任务。每一阶段分别报告可复现的指标，避免把环境通过、观测通过或损失下降等同于自主操作成功。
